## Context

- 大杀四方当前的“选牌 -> 高亮合法基地/随从 -> 点击目标 dispatch”主链路已经集中在 `Board.tsx`，UI 层已能派生：
  - 当前选中的手牌
  - 合法基地集合
  - ongoing 行动卡的合法随从集合
  - 交互驱动的基地/随从/持续行动卡高亮
- `BaseZone.tsx` 已经能根据 `isDeployMode`、`isSelectable`、`isMinionSelectMode`、`selectableMinionUids`、`selectableOngoingUids` 渲染合法目标高亮。
- 大杀四方当前有一个本地 `localStorage` 驱动的 `SmashUpOverlayContext`，只保存英文卡图中文覆盖层开关，尚未接入账号级持久化。
- 项目已有账号级用户设置能力，已覆盖音频、光标与 UI hints，后端存储入口为 `UserUISettings`。
- 局内设置入口已经存在于 `GameHUD`，当前主要承载音频等通用设置。
- 首页当前把登录/注册、用户菜单与语言切换直接铺在头部，PC 端另有全局悬浮球；移动端首页缺少一个可持续承载“登录、社交、设置”入口的紧凑导航容器。

## Goals

- 保留现有点击模式作为稳定默认行为。
- 增加大杀四方专属拖拽模式，并在移动端与桌面端都支持拖拽出牌。
- 把首页全局入口按平台分流：手机首页使用面包屑式导航，PC 首页继续使用悬浮球。
- 把大杀四方专属偏好统一收敛到悬浮球设置面板。
- 让游客与登录用户使用不同持久化路径，但对 UI 表现保持同一套偏好模型。
- 复用现有合法目标派生与 dispatch 逻辑，避免在拖拽链路里复制规则判断。

## Non-Goals

- 不重写引擎层 `InteractionSystem` 或通用命令协议。
- 不要求所有 PromptOverlay 场景都改成拖拽；本次只覆盖大杀四方手牌打出到棋盘目标的核心链路。
- 不在同一时间同时启用点击模式与拖拽模式作为“主出牌输入”；用户通过偏好显式选择其一。
- 不要求把局内移动端设置入口改成首页同款面包屑导航；首页入口与局内入口分开定义。

### Decision: 首页全局入口按平台分流

首页全局入口 SHALL 分为两套承载方式：

- 手机首页：使用面包屑式顶部导航收纳全局入口
- PC 首页：继续使用现有悬浮球承载全局入口

其中手机首页面包屑式导航至少需要覆盖：

- 登录 / 注册（游客态）
- 通知 / 社交
- 账户设置
- 全局设置

这样可以把当前分散在首页头部与用户菜单中的入口收敛到一个移动端更稳定的导航容器。

## Decisions

### Decision: 使用统一的大杀四方偏好模型

大杀四方 SHALL 定义统一偏好模型，至少包含：

- `inputMode: 'click' | 'drag'`
- `overlayEnabled: boolean`

该模型由大杀四方专属 Context 提供，供：

- 手牌交互
- 卡图渲染
- 悬浮球设置面板

统一消费，避免在 `Board`、`HandArea`、`CardRenderer` 各自维护独立状态。

### Decision: 偏好存储按登录态分流，但形状一致

为满足“百游戏扩展”与显式配置要求，账号级 UI 偏好将存储为按 `gameId` 分组的结构，而不是新增只服务大杀四方的孤立接口字段。

建议形状：

- 本地：`localStorage` 中保存 `smashup` 偏好对象
- 登录态：`UserUISettings` 中保存 `gamePreferences.smashup`

其中 `gamePreferences.smashup` 至少包含：

- `inputMode`
- `overlayEnabled`

这样既能服务本次需求，也能为未来其他游戏复用账号级游戏 UI 偏好通道。

### Decision: 局内设置入口扩展为“通用设置 + 游戏专属设置”

局内 `GameHUD` 的设置入口 SHALL 保留现有通用设置内容，并在当前游戏为 `smashup` 时追加“大杀四方偏好”区块。

该区块至少提供：

- 输入模式切换：点击模式 / 拖拽模式
- 英文卡图中文覆盖层开关

切换后 SHOULD 立即生效，且不要求刷新页面。

### Decision: 拖拽模式只改变主出牌输入，不复制规则判断

拖拽模式 SHALL 复用 `Board.tsx` 现有派生状态：

- `selectedCardUid`
- `selectedCardMode`
- `deployableBaseIndices`
- `ongoingMinionTargetUids`

拖拽链路的职责仅为：

1. 把手牌进入“正在拖拽某张牌”的 UI 状态。
2. 让现有目标高亮逻辑继续工作。
3. 通过基地/随从 DOM ref 做命中检测。
4. 在释放到合法目标时，调用与点击模式相同的命令入口。

这样可保证点击模式与拖拽模式共享同一套规则来源。

### Decision: 点击模式与拖拽模式互斥，避免主输入串扰

为满足“两个模式尽量不要互相影响”，系统 SHALL 采用互斥主输入：

- 点击模式：
  - 继续沿用当前“点牌选中 + 点目标落下”的行为。
  - 不因为轻微拖动而触发拖拽出牌。
- 拖拽模式：
  - 手牌主输入为“按下并移动超过阈值后开始拖拽，释放到目标完成出牌”。
  - 手牌普通点按不再进入当前点击选牌部署流程。

这意味着两种模式下的“主出牌动作”不会同时监听，避免用户不知道当前到底是谁在生效。

### Decision: 移动端拖拽与查看手势显式分离

移动端拖拽与现有“长按查看卡牌详情”会争抢同一根手指，因此本次要求：

- 在拖拽模式下，手牌卡面本体 SHALL 优先响应拖拽启动，不再依赖整张卡长按查看。
- 手牌详情查看 SHALL 通过显式放大镜按钮或非拖拽入口触发。
- 棋盘目标（基地/随从）的查看能力可继续保留现有长按/按钮机制，但不得阻止正在进行的手牌拖拽。

### Decision: 目标箭头与目标高亮同时存在

拖拽模式下，系统 SHALL 同时提供：

- 现有合法目标高亮
- 一条从被拖拽手牌指向当前命中目标或当前指针位置的箭头

箭头仅为表现层提示，不参与规则判断；真正合法性仍由现有派生集合控制。

## Risks / Trade-offs

- 增加随从 DOM ref 收集后，棋盘组件的局部复杂度会上升；但这比在拖拽结束时临时扫 DOM 更稳定。
- 移动端把手牌长按查看让位给拖拽，学习成本会上升；通过显式放大镜按钮补偿。
- 若后续希望支持“点击与拖拽同时可用”，需要重新定义优先级和误触策略；本次 spec 明确不走这条路。

## Migration Plan

1. 新增首页全局入口分流规则，定义移动端首页面包屑式导航与 PC 首页悬浮球的职责边界。
2. 新增大杀四方统一偏好模型与 Context。
3. 扩展游客本地存储与登录态账号存储，支持读取/写入同一偏好形状。
4. 在局内 `GameHUD` 设置面板接入大杀四方专属偏好区块。
5. 在 `HandArea`、`Board`、`BaseZone` 接入拖拽链路与箭头渲染。
6. 为首次登录且账号端无保存值的用户迁移当前本地大杀四方偏好。

## Open Questions

- 拖拽模式下，是否要为“不需要棋盘目标的即时行动卡”提供单独的拖拽释放规则，还是先保留原点击/弹窗链路。
- 大杀四方偏好区块是否只在对局页 `GameHUD` 中暴露，还是未来同步到主页全局悬浮球。
