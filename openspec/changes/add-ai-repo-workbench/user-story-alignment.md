# AI Repo Workbench 用户故事校准留档

> 来源：当前对话中用户多轮明确描述与纠偏。
> 用途：作为后续重构总控流、模块流、节点配置和审批语义的唯一用户故事校准稿。

## 1. 核心目标

用户要的不是一个被阉割的自定义工作台，也不是一个只剩按钮的假流程页，而是：

- 以官方 `Flowise` 为底座。
- 保留官方工作流、节点图、可编辑、可新增节点的能力。
- 在此基础上做增强，而不是覆盖、缩减或改造成另一套 UI。
- 最终目标是：用户给出任务、目录、需求后，系统能够自动拿起一套工作流去执行。

当前阶段先聚焦在“新增派系”这条主链路。

## 2. 入口与层级

用户对入口层的要求是：

- 用户视角应该有一个主入口 / 总控入口。
- 下面可以有模块化工作流，但这些模块是内部编排单元，不应喧宾夺主。
- 节点图本身是模块流程。
- 模块化是允许的，但不能让用户感觉自己要手工在一堆碎工作流之间跳来跳去。
- 层级感应接近 Unity 的分层状态机：
  - 上层看主流程大节点。
  - 点击大节点，可以进入子流程 / 子节点面板。
  - 能从子流程回到父流程。

## 3. 新增派系主流程用户故事

用户明确描述过的“新增派系”主链路如下：

### 3.1 输入阶段

- 第一步是选择 `TTS` 图包路径。
- 但图包路径是**可选信息**，不是绝对前置门槛。
- 任务描述本身可以直接写在描述里，不需要过度拆出很多表单字段。

### 3.2 素材检查阶段

- 系统先判断提供的素材是否符合旧图规格。
- 如果符合，就直接进入下一步。
- 如果不符合，才提出来，并要求用户说明怎么处理。

这里的关键语义是：

- 只有“发现异常”时才人工介入。
- 不是默认卡一个“人工确认素材”节点。

### 3.3 数据录入阶段

- 下一步进入数据录入。
- 可以直接走相关工作流或者 skill。
- 或者根据相关 skill 去搭建这部分工作流。

对数据来源的要求：

- 该节点应该支持添加数据来源。
- 默认开启主动搜索 Wiki 做数据对照。
- 默认会自动查找该游戏 `doc` 文件夹下的文档。
- 只有“第一优先级图片数据”和对照源不一致时，才做记录。
- 这些不一致项在**全部录入结束后**统一提供给用户。

这里的关键语义是：

- 数据来源策略应主要体现在模块节点配置里。
- 不应该在总控启动表单里堆很多“数据来源开关”让用户手填。

### 3.4 循环录入阶段

- 这是一个循环节点。
- 每次结束后，都根据大纲判断是否录入完毕。
- 大纲来源就是用户声明要添加的派系和图片内容。

### 3.5 实施阶段

- 数据录入结束后，进入实施阶段。
- 如果有多个派系，就一个一个分批进行。
- 对每个派系，分两条链路同时进行：
  - 没有新交互的，走可直接配置实现的链路。
  - 有新交互 / 新机制的，走另一条链路。
- 同类交互只挑有代表性的做端到端测试。
- 交付时要给截图。
- 端到端情景最好选择可能产生冲突的效果做交叉验证。

### 3.6 实施后审计阶段

- 实施完成后，再进入循环节点，对实施内容进行审计。
- 审计重点包括：
  - 是否复用了已有 UI，而不是自己创造。
  - 素材规格一致时，是否沿用旧派系一致的图片接线方式。
- 不通过就重写。
- 通过才进入下一阶段。

### 3.7 多代理审计阶段

- 在实施审计通过后，开始多代理对所有实施内容进行审计。
- 按照审计文档规范进行。
- 审计结束后继续进入循环节点，检查审计结果文档是否达标。

### 3.8 上传素材 / 验收阶段

- 审计完成后，进入上传素材步骤。
- 这一步基本就是验收阶段。

## 4. 审批与自动化语义

用户明确要求：

- 整条链路应该尽量连续。
- 默认目标是：用户给目录和要求后，可以一路自动化执行到结束。
- 阶段与阶段之间的审批应该是**可关闭**的。
- 如果关闭所有审批，就应该接近“一句话出结果”。
- 如果打开某些审批，才在对应阶段停下来。
- 上一个阶段的回报应该保留到下一个阶段，而不是每段割裂。

因此，审批语义必须满足：

- 审批是可选门禁，不是默认每段都停。
- 阶段结果要贯穿整个主流程。
- 只有异常、冲突、未达标、需裁决时才进入人工决策。

## 5. 用户明确否定过的内容

以下内容是用户明确表达过“不希望出现”或“这是误解”的：

- 不能把官方 Flowise 改成自造工作台 UI。
- 不能把官方节点图缩成一个小角落，其他无关面板做得很大。
- 不能把原本已有的工作流管理、加节点、编辑节点能力砍掉。
- 不能把系统改成“只能点按钮走流程”。
- 不能把“数据来源”错误提升成总控表单主输入。
- 不能把“素材异常时才需要人工处理”错误实现成默认卡人工确认。
- 不能把整套东西做成“会话式启动面板 + 决策卡 + 结果卡”的阉割版替代品。
- 不能把当前目标理解成“只做一个固定死流程，没有官方 Flow 工作流能力”。

## 6. 当前实现偏离点

以下偏离点已经在当前 seed 中出现，需要在后续重构中清理：

- 总控流启动表单塞了过多结构化输入。
  - 如 `enableWikiComparison`、`enableDocLookup`、`extraDataSources`
  - 这些更应该沉到模块节点配置，而不是主入口表单。
- 当前主流存在默认的“人工确认素材”节点。
  - 这不符合“只有素材异常时才人工介入”的用户故事。
- 当前图包路径被做得过于前置。
  - 用户要求它是可选输入，不是硬前置门槛。
- 当前总控流仍更像“骨架演示流”。
  - 离“用户给任务后自动拿起流程执行”还有明显距离。

## 7. 后续重构硬要求

基于上述用户故事，后续重构必须满足：

1. 总控流是主入口，模块流是内部编排单元。
2. 主入口输入尽量收敛到高层任务信息，不堆数据源细项。
3. 数据来源、默认查找策略、Wiki 对照策略下沉到模块节点配置。
4. 素材相关人工节点必须改成“异常时才进入”。
5. 审批节点全部改成可关闭门禁。
6. 阶段输出必须串成一条连续状态链。
7. 多派系、双链路实施、审计循环、多代理审计、上传验收都应围绕一条总控主链组织。
8. 不得再为了“解释”而新增重型 UI 外壳；应尽量利用官方 Flowise 现有能力。

## 8. 当前裁决

当前对用户故事的最准确总结是：

- **用户要的是“官方 Flowise + 总控入口 + 模块化子流 + 可钻取层级 + 默认自动化执行 + 可选审批门禁”的 AI repo workbench。**
- **当前 seed 只是走到“官方 Flowise + 可见模块流 + 可钻取层级”，还没有达到用户真正要的总控自动化语义。**
