## Context
- 当前 `AppUpdatePlugin` 与 `GamePackagePlugin` 都在插件内部直接发起 `HttpURLConnection` 下载，并把进度事件实时回推给 JS。
- 这类实现有三个根缺口：
  - 生命周期绑定进程：切后台、被系统回收、权限页跳转、低内存杀进程后，下载任务无法自然续跑。
  - 传输层不完整：没有 `Range` 续传、没有稳定的服务端续传协商、没有统一的临时文件/校验记录。
  - 状态恢复错误：JS 恢复时把“上次进行中”直接打成失败，等价于承认系统不会恢复任务。

## Goals / Non-Goals
- Goals:
  - 下载任务必须独立于单次 WebView 生命周期存在。
  - 支持断点续传、后台继续、进程重启后恢复状态。
  - 对 APK 更新包与游戏资源包复用同一套下载状态模型与诊断字段。
  - 保持现有“校验通过后原子切换”的安装安全边界。
  - 为后续 runtime/module/asset 多包并存提供统一底座。
- Non-Goals:
  - 本 change 不重新设计 OTA provider。
  - 本 change 不覆盖 iOS。
  - 本 change 不改变发布清单的业务语义，只增强客户端下载执行层。

## 商业化差距分析

### 1. 后台能力不足
- 现状问题：
  - 下载任务绑定当前 App 进程和插件线程池。
  - 缺少系统级后台下载或前台服务托管。
- 商业化要求：
  - 用户切后台后任务仍可继续，至少要么由系统下载器托管，要么由前台服务/WorkManager 托管并有可见通知。

### 2. 断点续传缺失
- 现状问题：
  - 没有 `Range` 请求、分片记录、ETag/Last-Modified 校验。
  - 临时文件被覆盖或清理后只能重头开始。
- 商业化要求：
  - 必须具备 partial 文件续传、服务端协商失败时回退全量重下、并记录为何不能续传。

### 3. 状态模型不可靠
- 现状问题：
  - JS 层把“进行中但当前没有活动句柄”的状态直接打成失败。
  - 进度真相依赖当前内存事件，而不是原生任务注册表。
- 商业化要求：
  - 原生任务表才是唯一真相源；JS 只是订阅与显示，不得自行推断任务已死。

### 4. 用户体验不达标
- 现状问题：
  - 重新进入页面后只能看到“请重新发起”。
  - 没有“正在后台继续”“等待恢复”“可继续安装”这类状态。
- 商业化要求：
  - 用户要能区分：后台继续中、已暂停待恢复、校验中、已下载待安装、失败可重试。

### 5. 运维与审计能力薄弱
- 现状问题：
  - 错误分类粗糙，难以区分网络失败、校验失败、磁盘空间、权限、服务端不支持续传。
  - 缺少任务级 id、尝试次数、续传命中率等诊断。
- 商业化要求：
  - 下载链路必须可追踪、可统计、可解释，便于线上监控与客服排障。

## Decisions

### Decision: 引入 Android 统一下载任务注册表
- 每个下载任务拥有稳定 `taskId`，持久化记录：
  - `taskId`
  - `kind` (`apk-update` / `game-asset-pack` / future kinds)
  - `logicalId`（如 `gameId` 或 `appVersion`）
  - `sourceUrl`
  - `expectedChecksum`
  - `etag`
  - `totalBytes`
  - `downloadedBytes`
  - `status`
  - `errorCode`
  - `attemptCount`
  - `updatedAt`
- JS 侧恢复时先读这个注册表，而不是读旧的 localStorage 推断。

### Decision: 下载执行层必须支持续传
- 优先方案：
  - APK 更新包使用系统托管下载或 `ForegroundService` 托管下载。
  - 游戏资源包使用 `ForegroundService` 托管下载，并保留后续接入 `WorkManager` 恢复调度的扩展位。
- 续传要求：
  - 维护 `.part` 文件与元数据。
  - 请求头带 `Range`，并校验 `206/200` 响应语义。
  - 服务端不支持续传时，显式降级到全量重下并记录原因。

### Decision: V1 并发策略采用“单 active + 持久队列”
- 当前阶段不采用“多游戏同时真并发下载”。
- 同一时刻只允许一个原生下载任务处于 `running`。
- 新任务发起时：
  - 若同一 `kind + logicalId` 已存在非终态任务，则直接复用已有任务。
  - 若已有其他 active 任务，则新任务进入 `queued`。
  - 若当前无 active 任务，则立即提升为 `running` 并由 `ForegroundService` 托管。
- 这样做的原因：
  - 降低大包并发时的带宽竞争与磁盘压力。
  - 简化通知、恢复、错误归因与客服排障。
  - 保留未来把最大并发数扩展为配置项的空间，但默认值仍应为 `1`。

### Decision: ForegroundService 是 Android 下载执行的唯一生命周期宿主
- JS 不再持有下载任务生命周期，只负责：
  - 发起下载请求
  - 读取任务注册表
  - 订阅任务状态并渲染 UI
- `AppUpdatePlugin` 与 `GamePackagePlugin` 后续都必须桥接到统一下载执行层，而不是各自维护线程池和取消注册表。
- `ForegroundService` 负责：
  - 接收 enqueue/cancel/reconcile 指令
  - 维护通知栏常驻进度
  - 从任务注册表恢复 active/queued 任务
  - 推进队列中的下一个任务

### Decision: 安装/激活继续使用 staging + 原子切换
- 下载完成后只能先进入 `verifying` / `extracting` / `ready-to-install`。
- 校验或解包失败不得污染当前可用版本。
- 旧版本继续可用直到新版本明确成功。

### Decision: JS 侧状态机改为“恢复原生任务”
- 页面打开、恢复前台、App 重启后：
  - 先查询原生任务注册表
  - 若任务仍有效，则继续订阅并显示当前进度
  - 若任务已完成但安装未完成，则显示“待安装/待激活”
  - 若任务已失败，再展示失败
- 禁止再把 `queued/downloading/verifying` 简单映射成“请重新发起”。

### Decision: 商业化门禁必须进入验收
- 验收不仅是“能下完”，还包括：
  - 切后台不中断或可恢复
  - 杀进程后能恢复状态
  - 部分下载能续传
  - 错误原因可解释
  - 完成后状态一致，不重复下载

## Risks / Trade-offs
- 原生实现复杂度上升，需要下载任务注册表、通知、恢复逻辑。
- `DownloadManager` 与自定义包解压链路的职责边界需要清晰，否则会出现“下完了但 JS 不知道怎么接着装”。
- 服务端若暂未提供稳定的 `Range/ETag`，客户端需要兼容“可续传”和“不可续传”两种路径。

## Migration Plan
1. 先建立下载任务 capability 与统一状态模型。
2. 替换 APK 更新包下载实现为可持久恢复链路。
3. 替换游戏资源包下载实现为可持久恢复链路。
4. JS 侧改为读取原生任务表并恢复显示。
5. 最后清理“上次下载未完成，请重新发起”这类原型期兜底逻辑。

## Open Questions
- 当前服务端对象存储是否稳定返回 `ETag` / `Accept-Ranges`，需要在实现前实测。
- 游戏资源包是否统一走单文件 zip，还是需要为未来的 module/runtime 包保留多文件分片协议。
