# Screenshot Delivery

这是 BoardGame 的 `adapter`，不是独立的看图规范。用户说“打开图、给我看图、图呢、重新打开”，或准备把最终验收图展示给用户时，必须先读并执行系统唯一 `canonical-source`：
`D:\codex-home\skills\show-image-to-user\SKILL.md`。

系统 skill 负责选哪张图、内联展示或外部查看器的选择、PureRef 进程核验、用户反馈“没显示”后的回退，以及“助手看过 / 脚本启动”与“用户确实看到”之间的区别。本 skill 只补充 BoardGame 项目专属的截图证据、命名、标记、脚本和相册约定。

## 规范来源与职责边界

- 用户可见开图：系统 `show-image-to-user` 是唯一 `canonical-source`；本 skill 不再规定查看器优先级、开图成功定义或回退路径。
- 本 skill：`adapter`，只规定 BoardGame 的项目脚本、截图目录、流程标记和服务器相册落点。
- 截图证据是否足够、必须拍哪些前后态、何时不能收口，以 `.spec/knowledge/standards/e2e-verification.md` 为 `canonical-source`。
- UI 改动是否通过玩家视角审计、是否需要继续返工，以 `.spec/knowledge/standards/ui-change-gates.md` 为 `canonical-source`。
- 多图标记和项目开图辅助脚本位于 `scripts/verify/label-image-sequence.py` 与 `scripts/verify/open-verified-image.mjs`。

## BoardGame 项目交付约定

- 服务器相册不是默认交付。只有用户明确要求“上传 / 发布链接 / 服务器相册 / 手机上看”时，才允许发布到
  `http://8.148.71.102:18080/#/boardgame/<task-id>`。
- 获得明确上传授权后，发布只允许更新
  `/home/admin/image-preview/data/projects/boardgame/tasks/<task-id>/`；
  禁止为了展示当前截图修改图片站页面、路由或根目录。
- 候选验收图、失败图、中间排查图不得上传为最终 `passed`。修复前复现图、诊断图、回归对照图只能标为“诊断 / 未验收”，不能写成收口证据。
- 用于交付的截图目录和截图文件名必须让用户一眼看懂：目录写清 `游戏 / 流程或交互`，文件写清 `编号 / 阶段 / 结果`；英文 gameId、日期、编号只能作辅助前缀。
- `端到端产物图 / 流程交付图` 是解释玩法链路的后处理产物，不是原始截图真相。作为交付时，必须保证关键截图足够大、文字可读、流程边界清楚，并包含本轮规则、剧本或验收口径摘要。

## BoardGame 截图证据要求

1. 用户要“整体图 / 整体图片 / 整体截图 / 端到端截图”时，主证据必须是当前真实页面的整屏图或等价真实主容器图。局部裁图、单元素图、overlay-only 图、contact sheet 和脚本标注图只能是第二层排查辅助，文件名和回复必须明确标为“局部 / 裁图 / 排查辅助”。
2. 牌桌、棋盘、地图、战场或主游戏视图问题，先交能看见完整上下文的整体真实截图；主图仍看不清细节时才补局部图。用户已批评“只给局部图”后，本轮不得再用局部图收口。
3. 用户问“之前图 / 旧版图 / 原来 UI / 改之前是不是这样”时，当前工作区截图、修后截图、新生成截图、当前 DOM 或当前 HEAD 只能标为“当前实现”。必须使用旧截图、旧 evidence、旧提交代码、改动前测试断言或用户提供的历史图；没有就说明旧版图未锁定。
4. 状态型验收图必须先触发目标状态：玩家操作、系统结算、错误、加载、选择确认或状态切换后再截图，且文件名、证据文档和回复写清前置动作。动作前、空态、相邻流程、历史图或只含容器的图不能充当该状态的验收图。
5. 位置 / 布局类验收图必须同时证明目标已出现、正确锚点及相对参照物、原错误位置没有残留同类对象，以及关键元素没有遮挡、挤压或抢焦点。整屏图无法肉眼判断时，补一张由原始真实截图派生的局部放大、红圈、箭头或对照辅助图，并保留原图路径。
6. 布局验收必须处于关键元素齐全的压力态：主按钮、玩家面板、阶段/状态/资源、手牌/公共区/牌堆/弃牌堆、当前 prompt、侧边工具、浮层入口、移动端安全区等会竞争空间的元素应同屏；规则上不可能同屏的，证据文档要说明原因。
7. 验收口径更新后，旧图必须重新分级。不满足新口径的旧图只能标为历史图、局部诊断图或失败/过期图，不能继续当最终验收图。
8. 用户用“上面 / 外面 / 旁边 / 右上角 / 手上 / 贴着 / 压着”等多义空间表达时，先用旧图、旧代码、当前整屏图或最小追问锁定锚点、参照物、层级和是否占位；未唯一锁定前不得改布局或跑验收。
9. 验收目标是新控件、开关、按钮、入口或视觉改点时，结论要指出它在画面中的位置。用户追问“在哪里 / 是否通过 / 能不能圈出来”时，从原始真实截图派生标注辅助图；无法指出改点位置时不得写“截图验收通过”。
10. 多人确认、可跳过、交易、手牌调换、响应窗口等多阶段交互，主证据至少覆盖本地确认后的等待态、全员或对方同意后的下一阶段；存在“不执行 / 跳过 / 空选择”分支时，还要证明跳过后的等待态。
11. 用户验收图与最终产物图必须是高清原图或等价高清导出版，不能默认用压缩图、缩略图或 contact sheet 代替。
12. 最终产物是流程图、剧本链路图或规则验收图时，不能只拼截图和短标签；必须包含玩家能读懂的剧本 / 规则摘要、当前实现边界、关键动作、胜负或验收结论。

## 项目脚本与多图标记

先按系统 `show-image-to-user` 锁定目标图和用户可见交付通道。只有系统流程选择了外部查看器，才可使用下面的 BoardGame 开图辅助脚本；这些脚本不自行选择查看器，也不替代系统流程的显示核验或失败回退。

```powershell
npm run verify:open-image -- "<绝对路径1>" "<绝对路径2>"

node scripts/verify/open-verified-image.mjs --viewer pureref --paths "<绝对路径1>" "<绝对路径2>"
```

- `OPENED_IMAGE=`、`OPENED_WITH_PUREREF=` 或脚本退出成功只证明项目脚本已发起开图动作；它们不证明用户已经看到图片，也不能代替系统 skill 的用户可见交付与回退判断。
- 系统流程确认需要以 PureRef 展示多张流程图时，一次性传入整组路径，不能逐张启动。
- 多张最终验收图需要外部连续查看时，先用项目脚本生成全尺寸的编号标记副本和 `00-sequence-index.png`，让用户能看懂顺序；标记副本不得覆盖原始截图。用户明确要原图、未压缩或不加标记时，按系统流程展示原图，仍在文字中给出顺序映射。
- 第一张标记写清起点或前置状态；从第二张开始写清上一张之后发生的动作和本张证明的结果。标签用玩家能理解的对象名和动作，且必须对应画面最前景真实对象。

```powershell
python scripts/verify/label-image-sequence.py `
  --out-dir "<截图目录>\\_labeled-for-pureref" `
  --title "<流程名称>" `
  --image "<原图1>" --label "<步骤 1 名称>" --transition "起点：<前置状态>" `
  --image "<原图2>" --label "<步骤 2 名称>" --transition "从 01 <动作> -> <画面结果>" `
  --overwrite
```

## BoardGame 汇报补充

- 用户要“这页 / 这个角色实际用了什么图”时，先遵守索引中的真实 UI 首图要求；图集原图、标出目标格的对照图和运行时裁图只能作为辅助诊断，并说明各自证明什么。空白、黑块、边缘碎片或无法辨认对象的裁图不能当角色头像交付。
- 多图必须按实际展示顺序给出“编号 -> 画面内容 -> 与上一张的承接”映射；文件名不能代替说明。
- 若使用了项目脚本，只能如实说明“已调用脚本并取得上述执行结果”；不得把它表述为用户必然已看到图片。
- 本项目相册链接仅在用户明确授权上传时给出。
