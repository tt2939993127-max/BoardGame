# Skill Governance

## 核心职责

先按系统裁决阶梯判断是否需要改规范；确实要改时，再决定“哪份是唯一真相源，哪些只是适配 / 索引 / 证据”。不要让同一规则在多个地方都变成可独立执行的规范正文。

本 skill 是落点裁决入口；真正创建/编辑 skill 时，再使用系统 `skill-creator` 的结构、校验和元数据规则。

## 五层落点

1. **系统 AGENTS**
   - 只写跨任务通用的不变量、红线、路由原则。
   - 不写具体 SOP、参数、命令顺序、文件命名或项目案例。

2. **项目 AGENTS**
   - 写当前仓库共享边界、入口、红线、应该读取哪个项目 skill/文档。
   - 不写可复用于其他项目的完整通用流程。

3. **系统 skill**
   - 写跨项目复用的任务方法，例如设计稿基线、看图交付、skill 治理、长期计划。
   - 不写只对某个仓库成立的脚本、路径、游戏名、路由、测试名或素材规则。

4. **项目 skill**
   - 写只对当前仓库/产品成立的 workflow、命令、素材约定、E2E 名称、目录结构和验收链。
   - 如果一个流程必须引用项目源码路径、项目脚本或项目数据，默认先放项目 skill。

5. **任务/用户故事/专项文档**
   - 写一次性决定、局部例外、当轮偏离、临时调查、长期计划拆解。
   - 不把一次事故里的临时细节升级成长期系统规则。

## 裁决流程

1. **先锁规则角色**
   - 准备修改的内容先标角色：`canonical-source`、`adapter`、`generated-copy`、`index`、`evidence` 或 `drift-check`。
   - 只有 `canonical-source` 承载可执行规则正文；其它角色只能引用、生成、记录或校验。

2. **判断项目专属信号**
   - 出现项目路径、项目脚本、项目测试名、项目路由、项目资产、项目内游戏名、项目内 UI 家族、项目数据结构时，默认项目 skill/项目文档。
   - 只有抽象后的方法能离开该项目独立使用，才放系统 skill。

3. **判断系统信号**
   - 用户要的是跨项目行为约束、通用执行红线、工具使用路由、通用验收门槛，默认系统 AGENTS 或系统 skill。
   - 具体执行步骤超过几条、需要模板或可复用工作流时，默认系统 skill；系统 AGENTS 只留入口和红线。

4. **避免多重真相**
   - 问题本质不是“改了几个文件 / 几个层级”，而是同一个规则是否出现了两个以上可独立执行、可独立解释、可能互相漂移的真相源。
   - **规范冲突必须立即阻塞（强制）**：只要两个候选正文能对同一现实动作给出不同指令，或主从 / 生成 / 引用关系无法判定，当前状态就是“规范冲突未收敛”。此时不得继续改实现、补测试、制作交付物、更新验收结论或把冲突只记成待办；必须先锁定 canonical-source、保留与迁移有效独有内容、改写其它入口为薄适配或索引，再继续原任务。
   - **重复正文必须收口删除（强制）**：确认两个手维护正文等价，或确认一侧的有效独有内容已等价迁入 canonical-source 后，必须在同轮删除旧正文并清理其入口与引用；不得保留“旧版备用”“暂时副本”“以后再删”作为第二个可执行来源。`generated-copy` 是唯一例外：它只能从 canonical-source 再生并由漂移校验约束，不能手改、不能迁移成新正文，也不能因“重复”被当作独立来源处理。
   - 允许、且必要时必须同时更新多处：唯一真相源、薄适配层、索引入口、生成副本、验收记录和校验脚本可以同轮修改。条件是每一处都必须标明自己是 `canonical-source`、`adapter`、`generated-copy`、`index`、`evidence` 或 `drift-check`，不能都写成规范正文。
   - **项目选用的系统能力必须迁入项目（强制）**：当项目要求协作者只依赖仓库内容时，只迁入该项目实际选用的系统 skill，不批量复制系统目录。迁入后，必须把同主题项目 adapter 的独有内容合并到项目 skill 并删除 adapter；项目 skill 成为该项目唯一执行入口，系统同名 skill 只作为其它项目的正文和本项目后续人工比对的上游候选。
   - **迁入不是自动派生（强制）**：系统 skill 更新不会自动覆盖项目副本。要吸收更新时，先比较系统候选与项目 canonical 的差异，按当前项目需求迁入有效内容并删除被替代的项目正文；无关系统 skill 和无关系统更新不得复制进项目。
   - 系统 AGENTS 只能写触发入口、硬红线或路由原则；它必须尊重当前项目已迁入的唯一 skill 入口，不得把系统同名 skill 重新变成本项目第二个执行来源。
   - 多重真相的判定标准：两处都能让后续 agent 直接据此执行同一规则，且没有主从关系、生成关系、引用关系或校验关系；这种情况必须合并、改成引用，或补 drift-check。
   - 验收、审计、测试报告、截图说明和复盘文档不是规范来源；它们只能引用已有设计规范 / 任务合同并记录证据、结论和差距。若验收时发现新要求，先回到对应规范或任务合同补为单一来源，再让验收文档引用，不得在验收里另写一套执行规则，也不得生成没有规范条款来源的独立 PASS/FAIL 清单。

5. **再动手**
   - 优先改 `canonical-source`；只有入口、适配、记录或防漂移确实需要时，才同步改其它角色文件。
   - 新建或大改 skill 时，使用系统 `skill-creator` 初始化/更新；写完后运行对应校验。
   - Windows 中文 skill 校验时设置 `PYTHONUTF8=1`，避免默认 GBK 读取失败。

## 规则回代

当用户指出“这不是某个 bug / 按钮 / 样式 / 测试问题，而是设计规范、流程规范或治理规范的问题”时，不得只修实现或只补一条项目规则。必须把事故抽象回规则层，并判断是否需要同时更新治理规则本身。

1. **先保留用户定性**
   - 汇报和判断里必须保留用户的关键定性，例如“设计规范问题”“规范的规范也要更新”。
   - 禁止把这类反馈改写成“按钮位置不对”“补一个测试”“以后注意”。

2. **重新锁真相源**
   - 先按系统裁决阶梯判断是否需要规范动作：不做、删除、审查现有候选职责归属、重构 / 拆分 / 迁移职责归属、改作者源 / 配置，最后才建立正式职责入口。
   - 先找这条规则应该由哪一份 `canonical-source` 承担；不要先铺开所有层级。
   - 如果当前事故暴露的是某类业务 UI、测试、看图、资源链或项目验收漏项，更新对应项目规范、项目 skill 或系统专项 skill。
   - 如果当前事故暴露的是“规范更新流程本身没有要求回代、分层或验收”，更新本 skill 或更高层治理入口。
   - 当用户质疑“是不是只给这个项目 / 这个游戏更新规范”“规范的规范是否也要更新”时，必须先把候选规则提升到跨项目不变量层审查。若抽象后适用于多个游戏、多个 UI 家族、多个测试流程或多个项目，禁止只改项目 skill / 单游戏 workflow 就收口；应优先更新或引用上位 `canonical-source`，再让项目文档做薄适配。
   - 若上位 `canonical-source` 已经有等价规则，本轮不应再新增一条平行规则；正确动作是明示“已有上位规则是什么”、补项目适配 / 审计引用 / 校验缺口，并把此前误判归类为“未执行已有规范”，而不是“缺少单游戏规范”。
   - 若上位 `canonical-source` 缺少该规则，且该规则能抽象成跨项目方法，先更新系统 skill 或系统专项文档；项目 AGENTS、项目 skill、游戏 workflow、evidence 只能引用或记录执行结果，不得各自扩写成独立规范正文。
   - 如果只是单个设计稿的对象摆放、槽位、文案或视觉反馈出错，默认先找到该对象的唯一规范来源并更新它；审计、README、任务记录、索引或适配文件可同步更新，但只能引用或记录，不得各自新增规则。
   - 如果单个事故暴露的是治理机制本身定义错了，例如“把多处修改误判成问题，而没有识别多重真相”，必须直接更新治理 skill；不需要等第二个事故复现。
   - 如果确实想从单个事故抽象通用规则，必须先写出“抽象后的唯一真相源是什么”“哪些文件只是适配 / 索引 / 证据”“如何防止漂移”。写不出时，停在局部层。
   - **规范更新落点必须先经索引裁决（强制）**：提出任何规范更新清单前，先通过当前项目的文档索引或等价路由找到既有 `canonical-source`，再明确当前属于“规范不存在”“规范已有但不可执行/不可验收”还是“规范已有但本轮未执行”。既有正文存在而索引缺少、错误或过宽地路由时，只更新索引并指向该正文；索引已正确命中时，裁定为执行失守，不得新增平行规则。根 `AGENTS.md` 只在缺少路由入口或红线时更新，禁止把事故 SOP、项目适配或既有正文再堆入根文件。只有能指出既有正文缺少触发条件、禁止行为、例外或最低证据，才允许更新治理规范。

3. **单一真相源 + 多投放层**
   - 规范回代默认采用“一个 canonical-source + 必要 adapter / index / evidence / drift-check”。不是限制文件数量，而是限制同一规则的独立权威数量。
   - 同一句规则需要出现在多个入口时，优先生成、引用或做漂移校验；如果只能人工复制，必须说明哪一份是 canonical-source，哪几份是副本，以及下次如何检查它们没有漂移。
   - 禁止把同一句新规则同时写成系统 skill、项目门禁、游戏专项合同和当轮审计里的四份独立正文。多层都需要知道时，上层写路由入口或抽象不变量，下层写可执行规则，审计只引用并记录证据。
   - 验收文档里的“失败项 / 差距 / 下一步”必须指向规范条款或任务合同条款；不能在验收表里创造未落规范的新规则，也不能把观察项包装成新的硬失败项。缺条款时，先补规范，再重新验收。

## 项目 skill 默认位置

按项目现有约定优先，不要新造目录。常见候选：

- 项目 `AGENTS.md` 指定的 skill 目录。
- `.codex/skill/` 或 `.codex/skills/`。
- `.spec/skills/`、`skills/`、`docs/workflows/`。

如果项目没有约定，先在项目 AGENTS 或当前回复中说明建议落点；不要直接把项目专属流程放进 `D:\codex-home\skills`。

## 汇报口径

最终说明只保留三件事：

- 哪份是 `canonical-source`，改了什么规则。
- 若同步改了适配 / 索引 / 证据 / 校验，说明它们的角色；没改则不用交代。
- 校验结果；如果没跑校验，说明原因。
