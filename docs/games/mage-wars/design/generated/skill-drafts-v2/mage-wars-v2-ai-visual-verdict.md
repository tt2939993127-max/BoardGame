## 共同门禁

| 检查项 | 结论 |
| --- | --- |
| 独立交付 | 四套均为独立 Open Design HTML artifact 与独立 PNG，不是同页总览裁切 |
| 生图边界 | 未调用 `od media generate`，均为 `mediaGenerate=false` 的 artifact 路线 |
| 真实素材 | 竞技场、法师牌、法术牌、卡背、token、攻击骰均实际进入画面主体 |
| 规则命名 | 没有把 Mage Wars 错写成规则不存在的“手牌”区；使用法术书、已计划法术、弃牌堆、隐性结界 |
| 区域归属 | 场上对象中心均在所属 `2x3` 区域内；A/C/D 最小所属区域占比 1.000，B 为 0.868 |
| 结算主体 | 攻击骰、效果骰、伤害 / 燃烧均贴近 B2 西锁骑士，没有落入右侧栏、日志栏或底部工作台 |
| 主 UI 文案 | 常驻主 UI 只保留对象名、数值、短状态和按钮；已移除“Open Design artifact”等内部说明 |

## 逐稿批判

| 方案 | 玩家友好点 | 仍需人工判断的风险 |
| --- | --- | --- |
| A 战场棋盘优先 | 六区域和场上对象归属最清楚；法术书退到二级，不抢战场；确认控件够短 | 法术书浏览存在感较弱，如果重点是计划阶段，会显得偏战斗态 |
| B 法术书工作台优先 | 法术书、分类、分页、候选、已计划槽最完整；适合检索和计划阶段 | 棋盘被压缩，虽然归属过门禁，但战斗态沉浸感弱于 A/C |
| C 施法结算舞台优先 | 当前火球术、目标、骰子、伤害形成最清楚动作链；最贴合“攻击掷骰在上层显示” | overlay 难度最高，后续实现时要严格控制遮挡和退场动画 |
| D 可访问专家操控优先 | 目标、费用、确认、取消、跳过、详情和等待响应都稳定可点；适合专家操作 | 右侧操控台仍有工具化气质，视觉游戏感不如 C |

## 推荐判断

- 如果目标是先解决你之前最关心的“攻击掷骰 / 结算为什么跑边上”，优先看 **C**。
- 如果目标是先解决“底部法术书候选、分类、分页、已计划槽”，优先看 **B**。
- 如果目标是先稳定规则空间和区域归属，优先看 **A**。
- 如果目标是先保证可点、可读、可实现和错误反馈，优先看 **D**。

我的建议是以 **C 为主结构**，吸收 **B 的法术书工作台**、**A 的区域锚点** 和 **D 的操控门禁** 做下一轮合成稿；但在你人工选择前，不进入实现。
