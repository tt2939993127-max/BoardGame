# Mage Wars 外部 UI 方法论基线

> 状态：`required-before-next-design / external-baseline / implementation-blocked`。本文件用于替代“继续微调旧稿”的路线。下一版 UI 设计、Open Design artifact、截图核验或人工验收前，必须先消费本文件，并输出一份新的规则到 UI 设计声明。

## 为什么新增这份基线

当前 v21 / v22 问题不是颜色、边框、阴影或间距局部失衡，而是设计方法本身没有重新建立：

- 没有先用外部 UI / UX 原则重建“玩家当前任务”。
- 多方案只在同一母版上调外观，没有改变信息架构、主焦点、操作路径和交互承载。
- 本地规则合同虽然约束了“不能错”，但不足以回答“怎样才对玩家友好”。
- 因此下一稿必须先从外部方法论提炼设计原则，再回到 Mage Wars 规则和素材做专用 UI。

## 外部来源账本

| 来源 | 类型 | 本项目采用点 | 不采用点 |
| --- | --- | --- | --- |
| ISO 9241-210 / Human-centred design | 人本设计过程 | 先定义玩家、任务、环境和评估，再做界面；设计由玩家任务驱动 | 不把它当视觉风格手册 |
| Nielsen Norman Group: 10 Usability Heuristics | 可用性启发式 | 系统状态可见、术语贴合玩家世界、识别优先于记忆、错误预防、审美最小化 | 不把“最小化”理解成空白极简或去掉游戏对象 |
| Don Norman: The Design of Everyday Things | 交互认知书籍 | affordance / signifier / mapping / feedback / conceptual model：对象如何暗示点击、控制如何映射结果、动作后如何反馈 | 不机械套物理产品例子 |
| About Face / Goal-directed design | 交互设计书籍 | 从玩家目标和关键路径定义界面，而不是从组件清单堆 UI | 不直接继承商业软件面板布局 |
| Designing Interfaces | UI 模式书籍 | 模式必须服务任务：浏览、筛选、详情、确认、回退都要有明确职责 | 不用通用网页卡片替代规则对象 |
| WCAG 2.2 / Apple HIG / Material target guidance | 可访问性与命中区 | 控件命中区、对比度、焦点、可读性是硬门槛；游戏 UI 也不能靠小字和小热区 | PC 稿不因移动端规则牺牲桌面棋盘 |
| Xbox Accessibility Guidelines / Game Accessibility Guidelines | 游戏 UI 可访问性 | 玩家必须理解 UI 组件作用；临时重要信息不能离开玩家视线；交互元素要明显、够大、间距足 | 不把完整无障碍设置面板塞进 Step 1 主界面 |
| Board Game Arena adaptation guidelines | 数字桌游适配范式 | 主游戏区域应居中；让玩家感觉规则被应用自动化；除大量文字游戏外，交互元素不应小于约 32px | 不照搬 BGA 外壳、账户 UI 或通用网页按钮 |
| Digital card game UI examples: Hearthstone / Slay the Spire / Magic Arena / Gwent | 卡牌驱动游戏范式 | 当前可行动卡必须可读；大量候选通常通过底部扇形、hover / focus 放大、分页、抽屉或详情预览处理 | 不复制“手牌”概念、皮肤、资源体系或其它游戏规则语义 |
| Strategy HUD / visual hierarchy references | 策略游戏信息层级 | 主舞台、当前命令、资源状态、临时结算和历史摘要必须分层；日志 / 归档不能抢当前操作视线 | 不把 RTS / 4X 的常驻仪表盘直接移植到桌游牌桌 |

## 2026-07-30 v30 失败后的外部范式回代

用户否决 v30 后，本文件新增以下硬结论。v31 曾尝试消费这些结论，但用户继续指出底部卡牌不可读、右下职责不足、中央仍拥挤，因此 v31 只保留为失败证据。v32 继续被用户否决：它虽然把火球术放大并占用右下，但底部牌区仍像不可读混合区，右下焦点只是重复当前卡，没有变成真实工作台，中心仍把目标、骰子、token 和边侧牌堆挤在同一视觉带上。v34 删除了底部混合牌区，也把当前火球术做成右下工作台，但 AI 原图复核确认 B2 目标、骰子、伤害、燃烧和目标角标仍形成中心注意力团块，不能送人工验收。v36 虽修正效果骰材质和中心团块，但仍把卡面已有费用 / 目标 / 结果复写成 UI chip，并把“支付前确认”和“已结算骰子 / 伤害”混在同一张运行态图里。因此 v37 及后续稿必须把这些结论作为硬门禁，而不是参考项：

### v34 失败后的二次外部范式收敛

| 外部不变量 | 本项目硬裁定 | v34 暴露的问题 |
| --- | --- | --- |
| BGA：中心是共享动作；相关信息不能散在三个角落 | 当前施法必须让 `来源 -> 目标 -> 结果` 在同一条视线链内，但不能把所有反馈挤在目标卡旁边 | B2 目标附近把骰子、伤害、燃烧、目标框和状态短标签堆成单个注意力团块 |
| BGA：交互对象不能缩小到不可用；空间不足时滚动 / 展开，而不是硬塞 | 法术书、弃牌堆、候选库只做入口；当前已计划法术必须是唯一可读大对象 | v34 方向正确，但右下入口仍需像真实工作台，不应成为贴边信息岛 |
| MTGO：读卡是 PC 卡牌游戏的默认能力，不能靠隐藏技巧 | 当前已计划法术保留大卡；其它卡只在需要计划 / 检视时放大 | 任何“小牌墙 + 远处大图”都继续禁止 |
| Apple / Microsoft：无关控件隐藏，HUD 让玩家不离开主玩法视线 | 无常驻确认；生命 / 法力 / 聚魔只贴玩家，不抢主舞台；当前结算不进日志或侧栏 | v34 的 HUD 没有越界，但结算层仍需要更轻、更分散、更贴对象 |
| 玩家视角：几何不重叠不等于可玩 | 审计必须写出玩家第一眼看哪里、当前能用什么、该点哪个对象、点完反馈在哪里；机器 PASS 只能作辅证 | v34 机器 PASS 但 AI 肉眼复核失败，后续必须写成 `geometry-pass-player-failed` |

| 外部范式结论 | 对 Mage Wars 的约束 | v30-v32 失败对应 |
| --- | --- | --- |
| 桌游数字化主游戏区域应保持居中，玩家第一眼看到可玩的主体 | 2x3 学徒竞技场仍是主舞台；牌区 overlay 只能服务当前动作，不能把竞技场挤成拥挤结算堆 | 中央棋盘同时被目标、骰子、token、路径线、底部候选和来源层挤压 |
| 卡牌驱动 UI 中，当前可支配卡牌必须可读；缩略候选需要焦点预览或展开机制 | 已计划法术必须成为唯一主卡工作台；法术书候选在施法结算态默认收起，不能再和当前主卡混在底部 | v30/v31 底部小牌不可读；v32 底部仍像不可读混合牌区 |
| 大量可浏览卡牌不应全量硬塞进常驻主 UI | 法术书只显示当前分类少量候选 + 页码 / 分类；完整浏览进入抽屉；弃牌堆保持边缘入口 | 法术书、已计划、弃牌、分页和状态混成一条窄底栏 |
| 空白是资源，不是装饰 | 右下角若被使用，必须承载真实主交互工作台，例如当前已计划法术大卡、已选目标摘要、确认 / 取消、另一张已计划法术、法术书入口和弃牌堆入口；只放重复大卡、费用标签或装饰仍失败 | v30 右下无职责；v32 右下重复火球术但未改变操作路径；v36 右下复写卡面字段但没有统一动作链 |
| 视觉层级不仅看不重叠，还要看认知拥挤 | 审计必须检查对象间距、焦点数量、路径线数量、token 是否互抢，而不仅是 bbox 是否相交 | v30 几何 PASS 但玩家视角失败 |
| 当前结算属于上层浮层，但必须克制 | 骰子 / 伤害 / 燃烧应锚在目标附近，但不能和场上卡、路径线、候选牌形成一团；需要减少装饰线和重复标签 | 中央主舞台被结算元素堆满 |

## v37 及后续必须采用的结构方向

- 学徒模式只用标准竞技场一半时，主稿默认裁成当前 `2x3` 学徒半场，让六格成为真正主棋盘；未用半场不得继续占据屏幕主要面积并迫使当前结算挤在右侧半边。
- 底部不再承担常驻牌区。目标确认态只保留当前已计划法术工作台、法术书入口、弃牌堆入口和必要短状态；完整候选浏览必须进入计划 / 浏览态抽屉，不得铺成小卡墙。
- 右下角必须使用为真实主工作台：当前已计划法术大卡、已选目标摘要、确认 / 取消、另一张已计划法术、法术书入口和弃牌堆入口都应在同一工作台内形成操作语义。不得再复写卡面已有的费用、射程、目标栏、骰数或效果文本。
- 右下工作台不能只是贴边信息岛：它必须在视觉上承接“当前已计划法术来源”，并通过短状态或轻量连线与棋盘目标形成因果关系；如果玩家需要在工作台和棋盘之间来回猜关系，仍判失败。
- 当前已计划法术和法术书候选必须分层：已计划卡是可执行来源，法术书候选只是浏览 / 计划来源，弃牌堆只是归档入口。
- 中央棋盘必须按阶段降噪：目标确认态只显示来源、目标高亮和确认 / 取消；确认后才显示骰子、伤害 / 燃烧 token。单张运行态设计稿不得同时出现“等待确认”和“已结算结果”，除非明确是多状态分镜。
- 设计审计必须新增局部裁图：当前主工作台 / 学徒半场中心结算 / 双方法师 HUD 三处都要能在原图裁切里读清。

## 已排除的通用规范

`ui-ux-pro-max` 本地知识库对查询 `tactical tabletop board game card battle dense gameplay UI Mage Wars` 返回了 `Marketplace / Directory` 和 `Exaggerated Minimalism`。这类规范适合目录、搜索、落地页或品牌展示，不适合 Mage Wars 对局主界面。

排除理由：

- 主 CTA 是搜索或转化，不是棋盘对象选择、施法、目标确认和结算。
- 大留白和巨型标题会压缩竞技场、法术书、已计划法术和结算骰。
- 蓝绿商业配色不能从 Mage Wars 真实素材推导。
- Inter / 极简网页风会削弱实体桌游卡牌和竞技场主体。
- 因此它只能保留可访问性、焦点、动效时长等通用底线，不能主导本次结构设计。

## 新设计原则

### 1. 先写玩家问题，再画区域

每个常驻 UI 区域必须回答一个玩家正在问的问题：

| 玩家问题 | UI 必须回答 | Mage Wars 画面结果 |
| --- | --- | --- |
| 现在轮到谁，处在哪一步？ | 当前阶段、行动者、可执行动作 | 阶段 / 当前行动槽必须在主视线，但不能压竞技场 |
| 我能用什么？ | 已计划法术、行动标记、快速施法、法力 | 已计划 0-2 槽和法力读数必须比法术书全库更靠近主动作 |
| 我能点哪里？ | 合法区域 / 合法对象 / 非法原因 | 高亮必须贴棋盘格和对象本体，不靠代理列表 |
| 这次动作从哪到哪？ | 来源、目标、路径、结果 | 施法 / 攻击结算必须在来源和目标之间形成一条视觉链 |
| 什么只是可查阅？ | 法术书浏览、弃牌堆、附件详情、日志 | 低频检视对象贴边或收起，不能抢中央舞台 |

如果一个区域不能回答玩家当前问题，只能做边缘入口、抽屉或历史摘要。

### 2. 概念模型必须来自规则，不来自其它卡牌游戏

| 规则对象 | 正确概念模型 | 失败信号 |
| --- | --- | --- |
| 法术书 | 私有可检索库；计划阶段从中准备最多 2 张 | 画成规则不存在的手牌区，或只剩一个牌堆角标 |
| 已计划法术 | 本回合真正可施放来源 | 与全书候选混成一排，玩家不知道能施放哪张 |
| 弃牌堆 | 公开归档 / 可检视 | 放进中央主链，暗示当前要从中选择 |
| 竞技场区域 | 移动、距离、目标和归属的空间单位 | 卡牌骑线、跨格、漂在格外 |
| 结算骰 | 当前攻击 / 效果的主反馈 | 进入侧栏、日志或角落，切断因果 |

下一稿不得再从“这里空着可以放什么”出发，只能从“这个规则对象在当前任务里有多重要”出发。

### 3. 映射必须自然：对象、控制、结果在同一因果链

使用 Don Norman 的 mapping / feedback 原则，Mage Wars 主动作必须形成：

```text
已计划法术 / 行动来源 -> 合法目标对象 -> 同一工作台确认 / 取消 -> 骰子 / 命中 -> 伤害或状态贴附目标
```

设计失败的直接判据：

- 目标在棋盘，骰子在右栏。
- 来源在底部，确认按钮在无关角落。
- 卡面已有费用、射程、目标栏、骰数和效果，却在旁边又写一套标签墙。
- 伤害 / 状态不贴目标，而是进入摘要框。
- 玩家需要读说明文字才知道谁影响了谁。

### 4. 识别优先于记忆

玩家不应该记住上一屏、隐藏面板或旧日志才能行动。下一稿必须让这些信息在当前画面可识别：

- 当前阶段、行动者、可用行动。
- 已计划法术的正面 / 卡背可见性边界。
- 法术书当前分类、页码、候选卡数量和已计划槽。
- 合法目标与非法目标的视觉区别。
- 当前结算骰面、伤害、状态和目标关系。

如果需要说明句才能理解，优先修对象摆放和视觉层级，而不是加文案。

### 5. 渐进披露：中央只给当前任务

Mage Wars 对象很多，不能全部常驻展开。下一稿按交互权重分层：

| 权重 | 对象 | 默认处理 |
| --- | --- | --- |
| 当前主任务 | 当前法术 / 行动来源、已选目标、确认 / 取消；确认后才是骰子与结果 | 主舞台或贴近主舞台 |
| 高频支撑 | 法师 HUD、已计划法术、行动标记、法力 | 贴近所属法师或玩家边缘 |
| 中频浏览 | 法术书候选、分类、分页 | 底部工作台，计划态展开，施法态压缩 |
| 低频检视 | 弃牌堆、日志、帮助、完整附件详情 | 边缘入口或抽屉 |
| 历史 / 教学 | 规则解释、操作说明、验收标签 | 不进入常驻主 UI |

任何低频检视对象进入中央，都需要一条当前规则步骤证明。

### 6. 控件命中区与视线成本要过硬

下一稿 PC 桌面也要检查命中区和视线成本：

- 主要按钮、分页、分类、已计划槽、可点击牌堆入口：可见尺寸不小于 32px，命中区目标按 44px 级别设计。
- 棋盘对象选择：点击对象本体或所属区域热区，不用小代理按钮。
- 重复动作入口固定，不随每张卡漂移。
- 当前结算临时信息不能离开目标 / 主舞台视线。
- 所有短标签和数值必须满足深色桌面上的可读对比；颜色不能是唯一信息。

### 7. 视觉不是边框系统，而是对象系统

下一稿视觉语言先来自 Mage Wars 真实对象：

- 棋盘纹理、卡牌印刷边、骰面、token、法师牌是主体。
- UI 容器只负责组织和触发，不当第一视觉。
- 边框只能表达三类信息：素材本体边界、合法目标 / 当前选中、必要按钮命中区。
- 如果去掉框后玩家仍能理解对象关系，该框默认删除。
- 如果第一眼看到的是面板框、圆点、说明文字或分区壳，而不是竞技场 / 卡牌 / 当前动作，整稿失败。

### 8. 多方案必须结构不同，不是同图换皮

真正的 A/B/C 方案至少要在以下四项中改变三项：

| 维度 | 变化要求 |
| --- | --- |
| 主焦点 | 棋盘中心、法术书工作台、结算舞台三者至少一种明显不同 |
| 信息架构 | 法术书、已计划、弃牌、HUD、结算链的层级必须不同 |
| 操作路径 | 玩家从来源到目标到确认的视线和鼠标路径必须不同 |
| 视觉语法 | 对象尺度、桌面密度、HUD 附着方式、结算表现必须不同 |
| 空间比例 | 棋盘、底部工作台、侧边行动区占比必须肉眼可辨 |

如果三套方案可以共用同一 DOM 结构、只换 CSS 权重或配色，直接判 `same-layout-failure`。

## 下一版 UI 设计交付要求

生成任何 Open Design artifact 或截图前，必须先交付一份新的文字 UI 设计，至少包含：

1. `玩家任务链`：计划、施法、移动、攻击、守卫、等待响应各自的玩家问题。
2. `规则对象权重表`：每个对象为什么在中央 / 边缘 / 抽屉 / 不显示。
3. `核心动作 storyboard`：已计划法术 -> 选目标 -> 支付 / 骰子 -> 状态结果。
4. `三套结构方案 brief`：三套方案的主焦点、适用玩家问题、牺牲项。
5. `失败稿反证`：明确 v21/v22 哪些结构继续禁用。
6. `审计表`：逐项检查外部原则、规则语义、素材链、少边框、命中区、隐藏信息。

用户没有批准这份 UI 设计前，不得生成下一张 Open Design 设计稿。

## 下一版 Open Design 设计稿硬门禁

- `mediaGenerate=false`，继续禁止图片模型生图。
- 使用 Open Design artifact 代码设计稿及其渲染截图作为设计候选，不进入真实 Board/UI 实现。
- 必须使用正式素材作为主体：竞技场、法师牌、法术牌、卡背、token、骰面。
- 自制运行态 UI 只允许用于生命、法力、聚魔、法力预扣态、短状态和动态反馈，并必须与素材材质一致；不得复写可读卡面字段。
- PC 桌面先过，移动端冻结。
- AI 图面核验 PASS 后才允许打开给用户人工验收。

## 设计审计表

| 检查项 | PASS 标准 | FAIL 例子 |
| --- | --- | --- |
| 玩家当前问题 | 第一眼知道轮到谁、能做什么、该点哪里 | 只看到漂亮面板，不知道下一步 |
| 概念模型 | 所有牌区名和流转来自规则 | 出现规则不存在的牌区 |
| 识别优先 | 关键选择、状态、结果可直接识别 | 靠说明文案解释 |
| 映射 / 反馈 | 来源、目标、确认 / 取消、骰子和结果按阶段在同一动作链路 | 骰子或结果跑到侧栏；确认态和结算态混在一张单态稿 |
| 渐进披露 | 中央只承载当前任务 | 弃牌堆 / 日志 / 帮助抢中央 |
| 命中区 | 主要控件大、近、稳定 | 小字按钮、远距离确认 |
| 素材主体 | 真实卡牌 / 棋盘 / token 是视觉主体 | 程序圆点、框体、CSS 卡壳抢主体 |
| 少边框 | 框只表达交互状态或真实对象边界 | 框中框、厚面板、玻璃壳 |
| 多方案差异 | A/B/C 信息架构和操作路径明显不同 | 同母版换颜色 / 换权重 |
