## 找到的 UI 设计相关 skill

| skill | 当前用途 | 本次结论 |
| --- | --- | --- |
| `ui-design-pipeline` | 设计 I/O、规则到 UI、先文字 UI 设计再设计稿 | 必须作为主流程；它决定“先写玩家任务 / 交互 / 状态”，不能直接画稿 |

| `ui-audit-loop` / `visual-verdict` | 后续截图审计 | 下一阶段出 Open Design 截图后使用；现在还不到看图门禁 |

## 外部原则如何进入本设计

| 外部原则 | UI 设计含义 | Mage Wars 应用 |
| --- | --- | --- |
| 人本设计 | 先定义玩家任务和使用环境 | 当前玩家在 PC 桌面快速判断：我能做什么、能点哪里、结果是什么 |
| 可用性启发式 | 系统状态可见、术语贴合现实、识别优先于记忆 | 不写“手牌”；使用法术书、已计划法术、弃牌堆；当前动作和费用必须可见 |
| Norman 映射 / 反馈 | 控制、对象、结果必须形成因果链 | 已计划法术 -> 目标对象 -> 费用 / 骰子 -> 伤害 / 状态贴目标 |
| Hick 法则 | 多选项要分组和渐进披露 | 法术书按类型分类 + 分页，不把 30+ 张法术一次塞满 |
| Fitts 法则 | 高频控件要近、大、稳定 | 确认 / 取消 / 分页 / 分类 / 计划槽必须可点，不做小字按钮 |
| 视觉引导 | 玩家不靠说明文字也知道该点哪 | 合法目标贴棋盘对象本体高亮，骰子靠目标而不是侧栏 |
| WCAG / 游戏可访问性 | 文本、焦点、命中区、对比度必须可用 | PC 稿也要有可读数值、可见焦点和 44px 级命中区规划 |

## 共同硬约束

所有方案都必须守住：

- 不出现“手牌 / opponent-hand / hand”概念；只用法术书、法术候选、已计划法术、弃牌堆、隐性结界。
- 学徒竞技场是 `2列 x 3行` 半场；所有场上卡必须有唯一所属区域。
- 法师状态板 `reference-only`；常驻生命 / 法力 / 聚魔用自制水平读数，但不能是粗糙蓝圆。
- 攻击骰 / 效果骰必须贴目标 / 来源 / 主舞台链路；不能进侧栏当摘要。
- 底部必须有法术书候选、分类、分页、已计划 2 槽；施法态可以压缩但不能消失。
- 弃牌堆是所属玩家边缘公开归档入口；当前无回收规则时不得进中央。
- 主 UI 不放规则解释正文；只放对象名、数值、短状态、按钮。
- 不生成图片模型；下一步如出稿，只能走 Open Design artifact + 渲染截图。

## 方案 A：战场棋盘优先

### 依据 skill

- `game-design`：玩家首先要理解空间、目标和当前行动。
- `visual-player-guidance`：可点对象必须用棋盘本体和卡牌本体引导。
- `Fitts`：棋盘目标够大、点击路径短。

### 适用判断

如果用户最在意“规则空间对不对、卡牌有没有骑线、谁打谁是否清楚”，选 A。

### 屏幕结构

| 区域 | 占比 / 位置 | 内容 |
| --- | --- | --- |
| 中央竞技场 | 约 68% 宽、72% 高，真正第一视觉 | 正式竞技场 + 右半场 `2x3` 区域 + 所有法师 / 生物 / 魔物 |
| 双方法师 HUD | 棋盘上 / 下对应法师附近，水平轻贴 | 法师牌、生命条、法力条、聚魔、行动 / 快速施法 token |
| 已计划法术 | 己方棋盘下沿中间，2 张大于候选卡 | 当前可施放来源，选中后抬升到棋盘边 |
| 法术书候选 | 最底部较薄横带 | 5-6 张候选卡、分类、分页 |
| 行动 dock | 右下固定，靠近已计划法术和棋盘 | 确认、取消、跳过、费用预览 |
| 弃牌堆 | 己方底边右侧小入口，对手顶边小入口 | 公开归档，点击才展开 |

### 交互链

1. 玩家点已计划法术 `火球术`。
2. 棋盘 `2x3` 区域里的合法目标本体高亮，非法目标降噪但保留。
3. 玩家点目标卡。
4. 目标卡旁出现费用预扣、攻击骰、效果骰轻 overlay。
5. 右下确认只负责提交，不负责替代目标选择。

### 优点

- 最不容易再犯“规则没看、区域不清、卡跨格”的错。
- 当前目标、骰子和状态天然在主舞台。
- 适合先把 PC 基线打牢。

### 牺牲

- 法术书浏览器不是最大焦点；计划阶段需要临时展开。
- 对卡牌管理感弱于方案 B。

### 失败判据

- 棋盘小于屏幕主视觉。
- 卡牌中心不在格内。
- 当前骰盘不贴目标。
- 底部法术书退成角标。

## 方案 B：法术书工作台优先

### 依据 skill

- `ui-design-pipeline`：先把规则对象分层，当前任务决定展开方式。
- `Hick`：30+ 张法术必须分类和分页，不能一次性全摊。
- `Designing Interfaces` 类模式：浏览、筛选、已选、确认分区。

### 适用判断

如果用户最在意“法术书怎么用、已计划法术来源是否清楚、下面一排卡怎么浏览”，选 B。

### 屏幕结构

| 区域 | 占比 / 位置 | 内容 |
| --- | --- | --- |
| 上方竞技场 | 约 62% 高，仍是规则空间主体 | `2x3` 区域、双方对象、当前目标 |
| 底部法术书工作台 | 约 32% 高，全宽 | 分类、候选卡横排、分页、搜索/排序可留后续、已计划 2 槽 |
| 当前施法槽 | 法术书工作台上沿中央 | 选中的已计划法术抬升，连接棋盘目标 |
| 玩家 HUD | 棋盘左右下角贴法师 | 水平条 + token，不占工作台 |
| 行动 dock | 工作台右侧大命中区 | 准备、替换、确认、取消 |
| 弃牌堆 | 工作台左右角，低权重 | 点击打开公开归档 |

### 交互链

1. 计划阶段：玩家在底部按 `攻击 / 结界 / 生物 / 魔物 / 装备 / 咒语` 分类浏览。
2. 每页展示 6-8 张可读候选；已计划槽固定 2 个。
3. 行动阶段：工作台压缩到 1 行候选 + 已计划槽；当前施法卡抬升到棋盘下沿。
4. 选目标和结算仍在棋盘上，不让工作台抢目标。

### 优点

- 最直接回应用户提出的“下面一排显示法术候选 + 分类 + 分页”。
- 计划阶段体验最强，选项组织符合 Hick。
- 已计划法术与全书候选关系清楚，不会误成手牌。

### 牺牲

- 棋盘垂直空间变少，对场上对象尺度要求更高。
- 如果处理不好，会回到“底部挤压当前施法卡”的旧问题。

### 失败判据

- 工作台压住棋盘对象。
- 已计划槽和候选卡混在一起无法区分。
- 对手法术书展开泄露信息。
- 分类按钮只是装饰，不能降低选择负担。

## 方案 C：施法结算舞台优先

### 依据 skill

- `frontend-design`：motion must carry meaning，动作本体和结果必须读得出来。
- Norman 映射 / feedback：来源、目标、费用、骰子、伤害必须在同一因果链。
- `ui-audit-loop` 后续可直接审“玩家第一眼知道谁影响谁”。

### 适用判断

如果用户最在意“攻击掷骰、施法、FX、结果反馈必须在上层主舞台”，选 C。

### 屏幕结构

| 区域 | 占比 / 位置 | 内容 |
| --- | --- | --- |
| 中央竞技场 | 约 60% 宽高，略让出结算链空间 | `2x3` 区域和对象 |
| 当前动作舞台 | 棋盘上层，从来源到目标形成横 / 斜向视觉链 | 当前法术卡缩放、费用、骰子、命中、伤害 / 状态 |
| 底部法术书 | 压缩但可用 | 候选卡、分类、分页、已计划槽 |
| 右侧行动 dock | 固定确认 / 取消 / 等待响应 | 不承载骰子主结果，只承载按钮 |
| 玩家 HUD | 贴近法师，低框感 | 水平条、token、附件摘要 |

### 交互链

1. 玩家点已计划 `火球术`。
2. 当前法术卡从底部已计划槽“抬升”到来源法师旁。
3. 玩家点目标，目标旁打开半透明结算落点。
4. 费用预扣贴法术卡和法力条；攻击骰 / 效果骰贴目标区域。
5. 成功后路径、骰子、伤害、燃烧 token 一条链完成；失败只显示反制 / 取消反馈。

### 优点

- 最能解决“骰子跑边上”“谁打谁不清楚”的问题。
- 法术 FX 和规则事件同步关系最强。
- 视觉最可能摆脱旧边框 UI，因为主体是对象运动和结果。

### 牺牲

- 最依赖动效设计和层级审计。
- 静态截图需要精心选状态，否则容易看起来像中间覆盖物。

### 失败判据

- 动作舞台变成大说明框。
- 骰子离开目标或来源。
- 费用、确认、伤害分散在不同角落。
- 结算 overlay 压住对象导致区域归属不清。

## 方案 D：可访问专家操控优先

### 依据 skill

- `ui-ux-pro-max`：焦点、命中区、对比度、反馈、加载状态。
- `existing-ui-design-baseline`：不继承旧图，但保留“稳定操作锚点”这个成熟不变量。
- Fitts：高频动作靠近常用路径，按钮大且稳定。

### 适用判断

如果用户最在意“玩家不会误点、所有入口清楚、实现后最稳定”，选 D。

### 屏幕结构

| 区域 | 占比 / 位置 | 内容 |
| --- | --- | --- |
| 中央竞技场 | 约 58% 宽、70% 高 | 区域和对象保持清楚，少装饰 |
| 右侧专家 dock | 固定 280-340px | 当前阶段、当前对象、确认 / 取消、费用、非法原因、等待响应 |
| 底部法术书 | 全宽但较克制 | 候选卡、分类、分页、已计划槽 |
| 玩家 HUD | 棋盘上下贴法师 | 数值可读、对比强、焦点清晰 |
| 快捷焦点 | 键盘 / 焦点顺序规划 | 已计划 -> 目标 -> 确认 -> 响应 |

### 交互链

1. 右侧 dock 只显示当前一步可以做的动作。
2. 目标仍必须点棋盘对象本体，dock 只显示已选摘要和确认。
3. 所有可点击对象有 hover / focus / active 三态。
4. 非法对象点击给短原因，不弹大段解释。

### 优点

- 最容易落地成稳定可用的真实 UI。
- 对比度、焦点、命中区明确，后续 E2E 和视觉审计清楚。
- 适合复杂规则逐步扩展。

### 牺牲

- 视觉冲击最弱，容易被认为保守。
- 如果右侧 dock 太强，会接近旧的“边栏承载太多”问题；骰子仍必须留在目标附近。

### 失败判据

- dock 承载骰子主结果。
- 按钮替代对象选择。
- 法术书候选太小或分类不可读。
- 画面像普通后台面板。

## 用户判断评分表

> 这张表用于让用户判断“哪套最好”，不是给 AI 自动拍板。每项按 `1-5` 分打分，任何 blocking 项低于 4 分，方案不得进入 Open Design 视觉稿。

| 判断项 | A 战场棋盘 | B 法术书工作台 | C 施法结算舞台 | D 专家操控 | blocking |
| --- | --- | --- | --- | --- | --- |
| 规则空间是否一眼清楚 | 5 | 3 | 4 | 4 | 是 |
| 法术书浏览是否玩家友好 | 3 | 5 | 4 | 4 | 是 |
| 已计划法术是否明确是施法来源 | 4 | 5 | 5 | 4 | 是 |
| 攻击 / 施法结算因果链是否清楚 | 4 | 4 | 5 | 4 | 是 |
| 骰子和结果是否在目标附近 | 5 | 4 | 5 | 4 | 是 |
| 隐藏信息是否自然表达 | 4 | 4 | 4 | 5 | 是 |
| 高频点击是否近、大、稳定 | 4 | 4 | 4 | 5 | 是 |
| 画面是否少边框、以素材为主体 | 5 | 3 | 4 | 3 | 是 |
| 后续实现风险 | 4 | 3 | 3 | 5 | 否 |
| 视觉新鲜度 / 摆脱旧稿程度 | 4 | 4 | 5 | 3 | 否 |

### 评分解释

- **A 高分项**：规则空间和区域归属最稳，适合先把“棋盘是否像 Mage Wars”做对。
- **B 高分项**：法术书、分类、分页和已计划槽最好，适合优先解决“下面一排法术候选”。
- **C 高分项**：当前法术、目标、骰子、伤害 / 状态结果最连贯，最能摆脱旧稿边栏和框体问题。
- **D 高分项**：可点性、焦点、可读性和实现稳定最好，但视觉上最容易保守。

### 直接淘汰规则

- 如果用户认为“棋盘区域不清”，淘汰 B 的纯工作台化版本，保留 B 的底部工作台作为子结构。
- 如果用户认为“法术书不清楚”，淘汰 A 的低底部版本，必须吸收 B。
- 如果用户认为“骰子 / FX 不在上层主舞台”，淘汰 D 的强侧栏版本，必须吸收 C。
- 如果用户认为“看起来还是网页面板 / 边框多”，淘汰 D 作为主视觉，只保留它的命中区和焦点门禁。
- 如果用户认为“太难实现”，不直接选 C 原版，而选 `C 主结构 + D 稳定 dock + B 压缩工作台`。

## 推荐选择口径

如果只能选一个作为下一张 Open Design PC 设计稿起点，我建议：

1. **优先选 C**：因为它最直接修复用户已经反复指出的“攻击掷骰 / 结算不在主舞台”和“因果链不清楚”。
2. **保留 B 的底部法术书工作台作为 C 的下半区**：用户已经明确要求底部候选、分类、分页，这不能丢。
3. **吸收 A 的区域锚点硬约束**：所有场上对象仍必须按 `2x3` 区域归属。
4. **用 D 做验收底线**：焦点、命中区、对比度、按钮稳定性不合格则不出图。

换句话说，建议下一稿不是 v21 微调，而是：

```text
C 的施法结算舞台
+ B 的法术书工作台
+ A 的区域锚点
+ D 的可访问性硬门禁
```

用户如果更偏向“先把规则棋盘完全做对”，则改选 A；如果更偏向“法术书操作才是核心”，则改选 B。

## 下一步门禁

- 用户选择 A / B / C / D 或指定组合前，不生成 Open Design artifact。
- 选定后先写对应 `v23-preflight.md`，再生成 HTML artifact。
- artifact 生成后先跑 AI 图面核验和几何审计；只有 PASS 后才用 PureRef 打开给用户。
- 用户人工批准前，真实 Board/UI 实现、移动端、真实页面 E2E 继续冻结。
